## Inferences

**I1 — The gate cannot be marked PASS**, because PASS would require positive
runtime evidence of the behaviour, and the implementation's only positive
evidence channel is empty.

**I2 — The null result is consistent with an unmet trigger**, not with broken
code. Nothing in the logs indicates the mod's scan path ever reached a decision
point.

**I3 — The trigger is structurally rare.** To fire, the mod needs, at a
`frame % 20 == 0` instant: an alive, enemy-owned, mobile (`unit`/`aircraft`) AI
unit holding a live target, with **≥ 2** objects in `{FLAKT, FLAK, FLAKC, PPLX}`
hostile to that unit within `AA_RADIUS = 8` cells **of the current target**
(weights: vehicle 1.0, building 1.1, infantry 0.6 against
`AA_THREAT_HIGH = 2.0`). One flak vehicle (1.0) is not enough; one flak cannon
building (1.1) is not enough.

**I4 — A second silent gate exists:** `pickAlternative` must also find a
*non*-AA hostile mobile unit within `ALT_RADIUS = 18` cells of the AI unit, with a
different id (`main.lua:122-150`). Zero alternatives produce zero output.

**I5 — A third precondition is invisible in the logs:** `Techno_GetTarget`
returns `nil` unless the unit's current target is a live techno
(`bindings_techno.cpp:701-719`), and `tThreat` stays `nil` when the target cannot
be located in the scan set (`main.lua:180-193`). Units that are not actively
holding a target at the scan instant contribute nothing.

**I6 — Therefore the absence of `[TARGET]` lines does not discriminate** between
"scenario never produced the condition", "condition produced but no alternative",
and "implementation cannot trigger". The mod emits no counter, no near-miss
diagnostic, and no per-scan trace.

**I7 — The persistence half of the boundary cannot be measured with this mod
set.** `RUNTIME_BOUNDARY.md:102-108` identifies "does the vanilla AI re-select
its own target?" as the open question. With `smart_ai` active and loaded *after*
`target_reselect`, the same units are re-commanded within ≤5 frames by another
**Lua** controller. Any later target state is therefore unattributable: it could
be vanilla AI, or Smart AI. This is a confound that makes both a false negative
(order overwritten by Lua, read as "vanilla overrode it") and a false positive
(order "held" because Lua re-issued it) possible.

**I8 — `accepted=true` is weak evidence.** `Techno_Attack` returns true whenever
the target pointer is a valid techno (`bindings_techno.cpp:611-634`); it does not
confirm the engine accepted a target *change*. Only the `readback` id is
meaningful.

**I9 — A single future `RESELECT` line would still not prove success.** The mod
logs unconditionally once `Attack` returns true, even if `readback` is `nil` or a
different id (`main.lua:214-233`). The acceptance criterion must be
`readback == alternative id`, plus survival across later frames.

## Code Analysis

Implementation: `scripts/mods/target_reselect/main.lua` (253 lines), registered
as `mod.Update(frame)` and gated to every 20th logical frame
(`main.lua:243-251`).

Pipeline, as implemented:

1. **Observe** — `World.GetAllUnits()`; keep alive + mobile + hostile-to-player
   units of kind `unit`/`aircraft` (`main.lua:160-175`).
2. **Signal** — read the unit's current target id (`:153-158`), locate that
   object in the same snapshot (`:182-185`), then sum AA threat within 8 cells of
   the *target* using `AA_TYPES` + `AA_KIND_WEIGHT` (`:104-117`).
3. **Decide** — rising-crossing hysteresis per `(unit, target)` pair: trigger if
   the previous observation of the *same* target was below
   `AA_THREAT_HIGH = 2.0` and the current is at/above it, else trigger on a first
   observation already at/above threshold (`:196-207`). State is
   `seen[id] = { lastTargetId, threat }` — primitives only.
4. **Act** — `pickAlternative` chooses the lowest-AA-threat hostile mobile unit
   within 18 cells that is not AA-typed and not the current target
   (`:122-150`); then `unit:Attack(alt)` (`:218`).
5. **Read-back** — `unit:GetTarget()` immediately after the order (`:221-226`)
   and log the observed id (`:227-230`).

This matches the architecture the documentation claims
(`RUNTIME_BOUNDARY.md:58-63`). The generic-decision and no-new-binding claims are
correct: the decision is a rule over a runtime signal with no unit-name branch,
and every primitive used already existed.

Correctly-documented boundary: the implementation is a **command**, not an
**override** (`RUNTIME_BOUNDARY.md:102-119`). There is no primitive that holds a
unit to a Lua-chosen target, and the mod itself does not implement a lease —
consistent with the explicit "do NOT implement yet" instruction.

Latent robustness issues (not evidence-relevant, no observed error lines):
`unit:GetPosition()` is called outside `pcall` at `main.lua:123` and `:137`, so a
vanishing unit would raise inside `pickAlternative`; the outer
`pcall(tick, frame)` (`:247`) would surface it as `[TARGET] update error` — of
which there are zero.

Observability gap (the review's central complaint): the implementation can
distinguish exactly one state — "reselection performed". It cannot report
"scanned N AI units", "K units held a target", "max signal observed = X", or
"signal crossed but no alternative". A gate whose test produces a null result
therefore yields no information.

## Risks / Alternative Explanations

- **A1 (most likely): trigger never met.** ≥2 flak objects co-located within
  8 cells of one specific AI-targeted unit, at a 20-frame boundary, with a second
  hostile unit within 18 cells. Nothing documents a scenario engineered for this.
- **A2: precondition never met.** No AI unit held a live target at a scan
  instant (I5).
- **A3: silent no-alternative.** Signal crossed, `pickAlternative` returned nil
  (I4) → zero output, indistinguishable from A1/A2.
- **A4: cross-mod confound.** Smart AI re-commands the same pool every 5 frames
  (I7/F9): a persistence test can produce both false negatives and false
  positives, and cannot attribute persistence to "vanilla AI did not override".
- **A5: "no errors" mistaken for PASS.** The repo's own rule forbids inferring a
  pass from missing errors when positive evidence is required; this is exactly
  the situation.
- **A6: log-interpretation false positive.** Any future `RESELECT` line with
  `readback=nil` or a mismatched id would look like success (I9).
- **A7: review-integrity.** The tree moved during this review (smart_ai 15:08,
  scaffolding 15:59–16:00, log 15:03). Any verdict must be pinned to revisions,
  as done in the header.
- **A8: label collision.** "M14.1" could cause Track A Gate 14.1 (EventBus) to be
  marked, or the Track B analysis deliverable to be skipped in favour of a
  runtime test.
- **A9: unreproducible harness.** The only existing "verified" claim for this
  experiment rests on an artifact absent from the repository (F2), so a future
  PASS must rest on live evidence, not on the harness claim.

## Verdict Rationale

**Not GO.** GO would assert that the M14.1 boundary is verified. There is no
positive runtime evidence: the implementation's own success strings are absent
from all four logs, including a fresh session of the exact committed code, while
the mod demonstrably executes every frame. In addition, the task's acceptance
criteria do not exist in the repository, and the single supporting "harness 8/8"
claim is not reproducible.

**Not NO-GO.** NO-GO would assert the approach cannot satisfy the goal. The code
implements a coherent observe → decide → act → read-back loop using existing
primitives, it ran without error, and the null result is fully explained by an
unmet, undocumented trigger condition (I2/I3). Refuting the approach on this data
would be as unjustified as accepting it.

**Not "PASS with caveats".** With `smart_ai` active, even a positive reselect
reading could not settle the question the boundary actually asks (I7).

The correct classification is therefore **INSUFFICIENT EVIDENCE**, and the
blocking deficiency is upstream of the code: no acceptance criteria, no
documented scenario, and no discriminating instrumentation.
